# 消息队列：接纳、调度与观察分离

消息队列建立在后台执行与可恢复 SSE 上。用户发送后，Server 返回持久化回执；Runtime 根据 Session 中的事实决定何时开始；Studio 只观察状态和发送明确的控制请求。浏览器关闭不会停止队列，浏览器也不负责重新发送下一条。

## 使用方式

运行中继续输入并发送会加入队列。Composer 上方显示待执行数量和摘要，可上移、取消或复制到草稿。等待项的内容不可变；复制不会删除原项。Stop 只影响点击时的当前执行，待执行消息保留，并在当前执行真正结束后继续。正常失败也会继续；持久化结果无法确认时会阻塞该 Session。

单 Session 最多 10 条等待消息，服务全局最多 100 条，正在运行的消息不计入等待容量。空闲 Session 可直接启动，因此不会因其他 Session 的等待容量耗尽而无法开始。

浏览器刷新后读取当前队列和执行状态，不重发已有输入。Server 重启会把没有持久化终态的等待和运行项标记为中断，不自动重放模型或工具；若 Turn 早已持久化完成，仅执行收尾事实缺失，则补记真实完成结果。

## 数据与依赖

Session 在原有 accepted/finished 之外增加 claimed 和 queue-reordered。accepted 同时保留逻辑输入与冻结后的实际采样输入；逻辑摘要决定请求是否是同一次重试。新事实必须包含 useProviderDefaults:false 的 runInput，不允许覆盖用户显式参数或修改消息、权限、模型和 Skills。

Provider 凭据、私有 client、context window 和插件 Generation 不进入等待输入。temperature/maxTokens 在接纳时固定；Generation 在实际开始时选用，继续由现有 Runner 固定一整个 Turn。工具仍进入共享 Tool Pipeline。

执行 SSE 传输单项输出；队列 SSE 只传输有限摘要、身份、顺序和调度状态。队列使用完整替换视图，慢订阅者只保留最新视图，等待项不分配输出环形缓冲。完整输入只在显式查看或复制时读取。

## 竞态与失败

- 接纳先检查持久化 requestId，再读取默认参数或容量。丢失 HTTP 响应后，相同请求仍得到同一执行身份。
- 上移提交全部等待 ID 的严格排列及 expectedRevision；取消也绑定 revision、目标身份和独立控制 requestId。重试先找到已完成控制事实，再检查当前版本。
- 等待项恰好被 claim 时，取消返回冲突，不自动变成 Stop 当前执行。
- append 抛错可能发生在提交之后，因此先读取持久化事实确认结果。无法确认时保留容量和所有权并阻塞，不能当成回滚。
- 当前执行收尾持久化、迭代器真正结束后才开始下一项。关闭入口立刻阻止新调度，排队项在关闭存储前取消。
- Studio 的草稿清除绑定 owner/revision，旧回执不能删除新输入；上一执行校准历史时不能抹掉下一执行的实时视图。
- 对话历史使用 Session 级单调持久化序号，防止上一执行的迟到读取覆盖下一执行已经同步的历史和失败/取消状态。导航后迟到的接纳回执可清除原草稿，但不重建旧会话观察器。
- 终态写入后先更新队列投影再通知观察者，避免短暂发布“active 已完成”的无效视图。测试需让读者提前等待下一帧，否则只保留最新视图的机制可能掩盖这个错误。

## 参考与取舍

设计中记录了已核实的 Codex、Kiro CLI 和 DeepSeek Harness 版本及来源。采用稳定队列身份、显式控制、区分 Queue/Steer 和 Host 调度。Stop 后继续消费队列采用 Harness 的交互原则；Codex 的中断后暂停策略未纳入本版。跨 Server 重启暂停/恢复和队列项原位编辑留待独立功能，不能从其他产品推断 Weave 已具备这些保证。

具体契约与验证要求见 [设计](../superpowers/specs/2026-11-23-message-queue-design.md) 和 [实施计划](../superpowers/plans/2026-11-23-message-queue.md)。测试和真实浏览器验收结果在 PR 验证记录中填写；本地确定性 Provider 只证明工作流，不代表真实模型吞吐或外部工具副作用 exactly-once。
