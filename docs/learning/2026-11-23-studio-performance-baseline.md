# Studio 长会话性能基线

本轮先记录生产构建在长会话中的表现，为后续分页、虚拟列表和流式更新优化保留可复现的对照。测试只使用本机合成 HTTP/SSE 数据，不调用模型，不打开真实项目或用户数据库。

后续实现与独立重采结果见 [长会话与工具流渲染](2026-11-24-studio-rendering-results.md)
和 [Explorer 渲染](2026-11-24-studio-explorer-rendering-results.md)。下文保留原始基线口径与数值。

## 复现

使用仓库要求的 Node.js 和 pnpm，安装依赖，并准备可直接执行的 `playwright-cli` 与 Chrome。脚本不会自动安装全局工具或下载浏览器。运行：

```bash
pnpm studio:benchmark --output=dist/performance/studio-baseline.json
```

命令先构建 Studio，再启动随机回环端口上的测试服务。默认测试 100、1000、5000 条用户/助手消息，分别使用 Markdown 和含工具调用的历史，每个场景重复三次。工具结果是额外的历史记录，不计入上述用户/助手消息数。

可以先运行小场景检查环境：

```bash
pnpm studio:benchmark --counts=100 --variants=markdown --repeats=1
```

每个样本单独启动、关闭一个浏览器，使用临时浏览器配置，静态资源禁止缓存。脚本退出时关闭自己创建的浏览器、HTTP 连接和流定时器，并删除临时脚本。输出保留逐样本指标与环境信息；普通 `pnpm check` 只验证确定性的 fixture 行为，不运行浏览器计时，也不设置机器相关的性能门槛。

## 2026-11-23 观察值

本次环境为 macOS / arm64、Apple M4 Pro、Node.js 24.4.0、Chrome 158.0.8127.36，视口 1440 × 1000，Studio 使用 Vite 生产构建。代码基线为 `2d5586eab65f35c3e47e02bcb6fa1b7bd929a492`，新增基准工具尚未提交，报告中的 `dirty` 为 `true`。

5000 条 Markdown 历史中，流期间单次累计阻塞部分为 2063–2334 ms；含工具调用时为 2432–2456 ms。这里累计每个超过 50 ms 的长任务中超出的部分，不把它等同于标准化的页面 TBT。

这些数据表明，历史消息增长后，全量挂载的 DOM 与流期间交互耗时都明显增加。后续可以先验证历史列表虚拟化，再验证输入、流式文本与历史行的更新隔离。当前数据只能指出优化方向，还不能确定各因素的因果贡献；没有优化前后对照时不能写性能提升百分比。

## 指标定义与限制

- `coldReadyMs`：从全新浏览器中的页面导航开始，到历史行数准确且经过两次 rAF。浏览器进程启动时间不在其中；这不是操作系统磁盘冷启动测试。
- `warmSwitchMs`：从点击历史会话按钮，到预期行数重新出现且经过两次 rAF，包含浏览器自动化开销。
- `inputFillToPaintMs`：流式响应出现首段文字后，自动填写草稿到两次 rAF 的耗时，并检查草稿值。它只是输入响应的代理指标，不能称为 INP，也不能证明合成器已经把像素显示到屏幕。
- `frameGapsMs`：流阶段 rAF 回调之间的间隔，不能直接换算为用户观察到的 FPS。
- `longTasks`：浏览器 Long Tasks API 的观测值。脚本保留开始时间和时长，方便重算聚合。
- `heapBytes`：可选的 Chromium JS heap 读数，不能据此判断保留内存或内存泄漏。
- `streamReadyMs`：发送到最终内容就绪的观测时间。测试服务固定输出 100 段文本、段间隔 20 ms，脚本核对全文和顺序；该指标不代表真实模型吞吐或多 Agent 性能。

同机还运行过开发验证任务，CPU 调度和浏览器自动化开销未完全控制。每场景只有三次重复，适合本地工程对照，不构成跨机器性能结论。初期复用浏览器的探索性结果因缓存和重复 observer 污染已经弃用，上表只使用逐样本新建浏览器的报告。

未来引入虚拟列表时，需要把“挂载全部行”的就绪断言改成“逻辑消息数正确、当前可见范围准确”，保留相同数据、视口、流速与输入步骤，再记录优化后的完整原始样本。
