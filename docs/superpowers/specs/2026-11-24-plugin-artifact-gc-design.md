# 插件制品回收与市场源配置日志压缩设计提案

状态：已评审（2026-11-24）。结论见下方「评审结论」；正文第 3、4 节的方案均已被结论取代，保留为评审时的分析。

## 评审结论（2026-11-24）

插件相关的配置与状态不再要求只追加，详见 [ADR 0005 修订](../../adr/0005-plugin-installation-and-distribution.md#amendment-2026-11-24)。据此：

- **G2 市场来源**：不做日志压缩（方案 E、F、G、H 均不采用）。改为只存当前来源列表（与 DeepSeek Harness 的 `indexes` 列表一致），修改时用临时文件加原子替换整份写入，并带版本号检查，避免两个窗口同时编辑时互相覆盖。1024 条上限随之取消。
- **G1 制品回收**：不做租约式标记清除（方案 C）。改为：
  1. 已安装插件有兼容的新版本时，在插件市场的"已安装"中显示"有新版本"和"更新"按钮；
  2. 点击后弹出一次确认，列出新旧版本在声明与权限上的差异；确认后替换当前记录并启用新版本；
  3. 切换完成后删除旧制品；仍被运行中的 Generation 或旧回合引用时，等它们释放后再删；
  4. 卸载同样删除记录和制品；
  5. 不保留旧版本，不提供本地回滚；需要旧版本时从来源重新安装。
- 信任仍绑定内容摘要，任何内容变化都需要重新确认。
- 64 个制品的上限保留，正常使用下制品数约等于已安装插件数。

实现前需要补充的设计：权威数据从事件折叠改为当前状态时的数据迁移；"旧制品是否仍被引用"的判定来源。

对应观察编号：G1、G2。

实现补充见[第 9 节](#9-实现补充g1-一键更新与制品回收r2-11)。

## 1. 背景

以下现状均已对照当前代码与文档核实。

### 1.1 制品存储（G1）

- 制品存储实现在 `packages/plugin-host/src/artifact-store.ts`，对外接口 `PluginArtifactStore`（`artifact-types.ts`）只有 `preview`、`stage`、`read`，没有删除或枚举接口。仅有的删除路径是清理暂存目录的 `removeStagingOperation`（`artifact-copy.ts`），不涉及已发布制品。
- `maxPublishedArtifacts = 64`。`assertCapacity` 遍历 `artifacts/` 目录，发现条目数达到 64 时抛 `plugin-artifact-capacity`，错误信息写明"包含孤儿制品，已有制品保留，容量满时只有完全相同的内容可以再次暂存"。目录中出现不是 64 位十六进制摘要名的条目会抛 `plugin-artifact-conflict`。
- 暂存目录内遗留的未完成操作上限为 64（`artifact-copy.ts` 的 `maxAbandonedOperations`），超出报错。
- 服务端包装在 `apps/server/src/owned-plugin-artifact-store.ts`，负责托管存储的所有权、租约与绑定，不增加删除能力。
- 制品以内容摘要命名，同一内容重复安装只占一份。卸载或更新插件后，旧版本制品不被删除；它们成为"孤儿"，仍占用 64 个名额。
- ADR 0005（`docs/adr/0005-plugin-installation-and-distribution.md`）写明：制品垃圾回收需要明确的 current/candidate/retired 租约与回滚保留，是独立设计，不是 6.1 正确性所必需。后果一节写明："初始磁盘保留是有意设定的有界保守策略，新内容在配额满时可被拒绝，卸载暂不回收。"
- 未核实：当前 Studio 在 `plugin-artifact-capacity` 错误时给用户的提示文案与可操作路径。未核实：卸载流程具体保留哪些记录（回滚是否依赖旧制品）。

### 1.2 市场源配置日志（G2）

- `apps/server/src/plugin-marketplace-settings.ts` 的 `openMarketplaceSettings(file)` 维护追加式 JSONL 日志，事件为 `add`（带 `id`、`name`、`url`）与 `remove`（带 `id`）。
- 上限：`maxEvents = 1024`（序号 1 到 1024），`maxBytes = 1 MiB`。活动远程源最多 10 个（回放时 `active.size >= 10` 即判错，`plugin-marketplace-manager.ts` 约第 157 行在添加时也检查）。
- `append` 在 `sequence >= maxEvents` 或追加后字节数超过 `maxBytes` 时，把 `available` 置为 `false` 并抛 `Marketplace settings full` 或 `unavailable`。之后所有写入都被拒绝，直到重启也不会恢复，因为重启后回放会得到同样的 `sequence` 与长度；读取到 1024 条以上或超过 1 MiB 的文件会在回放阶段直接判不可用并清空活动源（`catch` 分支中 `available = false; active.clear()`）。
- 用满之后：日志恰好含 1024 条事件（或接近 1 MiB）时，回放仍然合法，活动源照常加载；但 `append` 对 `sequence >= maxEvents` 或超过字节上限会把 `available` 置为 `false`，此后添加与删除源都被拒绝，重启后同样如此。`plugin-marketplace-manager.ts` 在 `!settings.available` 时给第一个源标记 `errorCode = 'settings-unavailable'`，没有恢复路径。只有当文件在回放时超出上限或内容无效（例如被外部改动）时，才会走 `catch` 分支，`active.clear()` 使已有远程源全部消失（未实测）。
- 该日志有意不修复未知内容："单个 Server 拥有这个追加式日志，永不修复未知字节"。设计文档 `docs/superpowers/specs/2026-11-22-plugin-marketplace-indexes-design.md` 写明"有界、校验过的日志，写入前同步落盘，重启回放；日志损坏后拒绝写入而不是覆盖"，并要求限制活动远程源数量与日志长度。压缩在该设计中没有出现（未发现相关描述）。
- 注意：用满的情形并非只由真实用户操作产生，重复添加、删除同一源同样消耗序号。按 1024 条计算，日常使用达到上限需要很长时间，但没有任何剩余容量提示。

## 2. 问题

1. **G1**：长期使用后（反复升级、试装、卸载）孤儿制品累积到 64 个，之后所有新内容都被拒绝安装，用户无法通过 Studio 解决，只能手动删除存储目录，而存储目录由 Server 拥有租约，手动删除有一致性风险（未核实具体后果）。
2. **G2**：市场源配置日志用满后，添加与删除源永久不可用，没有压缩，也没有预警；文件超限或损坏时回放会丢弃全部已有远程源。
3. 两者的共性：首版有意取舍的"有界"设计缺少"到达边界之后怎么办"的出口。

## 3. 可选方案：G1 制品回收

### 方案 A：保持现状，只做可见性与手动清理工具

增加只读诊断（制品数量、孤儿数量、占用字节）与明确的容量错误提示，并提供命令行或 Studio 入口让用户手动删除孤儿。

- 优点：风险低，不需要租约模型。
- 缺点：仍需要"哪些是孤儿"的权威判定，等同于做了一半的 GC；手动清理容易误删回滚所需制品。

### 方案 B：卸载时立即回收（引用计数）

卸载插件时，若没有其他安装记录引用该摘要则删除。

- 优点：简单，符合直觉。
- 缺点：与 ADR 0005 强调的"回滚保留"冲突；更新后旧版本被立即删除则无法回滚；并发的安装、卸载与加载（Generation）可能读取正在删除的制品，需要租约保护。

### 方案 C：基于租约的标记清除

按 ADR 0005 的方向：每个制品有 `current`（已被某个有效安装记录引用）、`candidate`（正在安装或待启用）、`retired`（已被取代，保留 N 个版本或 N 天用于回滚）三种状态，由权威数据库（plugin authority）记录引用。GC 在没有活动 Generation 持有读取租约、且没有进行中的安装时运行，只删除 `retired` 且超过保留期、且不被任何 Generation 引用的制品。

- 优点：与 ADR 一致，回滚安全。
- 缺点：需要权威数据库新增引用与保留状态的事件类型（append-only 约束下新增事件版本）；需要 Generation 读租约；工作量最大。

### 方案 D：提高上限

把 64 提高到更大值。只推迟问题，不是回收；仅作为临时缓解，可与方案 A 同时做。

### 推荐

C 为终态，A 为第一步：先交付可见性与诊断，不删除任何东西；再按 ADR 的租约模型设计 C。B 不推荐。D 不作为独立方案。

## 4. 可选方案：G2 配置日志压缩

### 方案 E：快照加增量

日志文件头部允许一条 `snapshot` 事件，包含当前所有活动源。压缩时写入新文件（临时文件、`fsync`、原子 `rename`），仅含快照，序号从 1 重新开始，再删除旧文件。回放时遇到 `snapshot` 事件需放在首位。

- 优点：保持 append-only 语义（每个文件内部仍只追加），压缩是显式、原子的维护操作。
- 缺点：改变了"永不修复未知字节"的约束，需要明确压缩只处理校验完全通过的文件；崩溃安全依赖 `rename` 的原子性；`O_NOFOLLOW`、文件身份（`dev`、`ino`）检查与新文件身份的衔接需要重新设计（当前 `append` 要求 `stat.size === length` 且 `ino` 与打开时一致）。

### 方案 F：滚动文件

写满后新开 `settings.2.jsonl`，新文件以对前一文件的摘要引用加快照开头。优点是不删旧数据；缺点是文件数量增长，回放要读多个文件，复杂度高于 E。

### 方案 G：不压缩，改善用尽后的行为

- 用满前预警（剩余序号低于阈值时在 Studio 提示）；
- 用满后不丢失已有活动源：回放遇到"超限但内容有效"的文件时，以只读模式加载全部有效事件，而不是清空；
- 提供显式的"重建配置文件"操作（用户确认，备份旧文件）。

### 方案 H：提高上限

把 1024 提高。同 D，只推迟。

### 推荐

采用 G 作为立即措施（"超限但有效则只读加载，不丢源"风险最低且独立可发布），随后实施 E 作为压缩。F 与 H 不推荐。压缩触发时机建议在启动回放完成后，当序号超过上限的某比例（例如 75%）时自动执行，或由用户显式触发，二选一在评审中决定。

## 5. 受影响的包与契约

- `packages/plugin-host`：`artifact-store.ts`、`artifact-types.ts`（若新增诊断或删除接口，`PluginArtifactStore` 接口扩展；需要同步 `index.ts` 导出）、`artifact-copy.ts`。
- `apps/server`：`owned-plugin-artifact-store.ts`（所有权与租约下的 GC 入口）、权威数据库相关文件（`plugin-authority-*.ts`，如需新增引用与保留状态事件）、`plugin-marketplace-settings.ts` 与 `plugin-marketplace-manager.ts`（G2）。
- `apps/studio`：容量错误提示、诊断展示、市场设置不可用时的提示与恢复入口。
- 契约：ADR 0005"制品垃圾回收需要独立设计"与"卸载暂不回收"的表述将被后续设计取代，实现时更新 ADR；市场索引设计的"有界日志"一节补充压缩规则。本提案不改动这些文档。
- 权威数据库事件为 append-only，新增事件类型涉及版本与重放兼容，具体做法未核实，需要读 `plugin-authority-*.ts` 后再定。

## 6. 迁移与兼容

- G1 方案 A 不改变存储格式，可直接发布。方案 C 需要为已有制品回填状态：首次运行时把被现有安装记录引用的标为 `current`，其余标为 `retired` 并设定保留起点为当前时间，避免升级当天就删除旧制品。
- G2 方案 G 对已有日志文件无格式变化；方案 E 引入 `snapshot` 事件，旧版本 Server 读到快照文件会判错并进入不可用，所以降级回旧版本会失去市场源配置，需要在发布说明中写明，或让新版本在压缩前保留一份 `.bak`。
- 两项维护操作都应在 Server 独占存储的前提下执行，沿用当前"不支持多进程共享写入"的约束。

## 7. 测试计划

- G1：容量边界（63、64 个）；孤儿与被引用制品的区分；GC 不删除被 Generation 租约持有的制品；GC 与并发安装、卸载、回滚的交错；崩溃在删除途中后目录仍可被 `assertCapacity` 正常遍历；保留期内不删除。
- G2：1024 条与 1 MiB 边界；超限但内容有效时只读加载并保留活动源；压缩后回放结果与压缩前活动源集合一致；压缩过程中崩溃（临时文件残留、`rename` 前后）；符号链接与身份变化被拒绝；序号不连续或未知字节仍判错，不被"修复"。
- Studio：容量与不可用提示的组件测试。

## 8. 未决问题

1. 回滚需要保留多少个版本或多长时间。
2. GC 是自动运行还是用户显式触发，是否允许在 Studio 里一键清理孤儿。
3. 权威数据库中"当前被哪些安装记录与 Generation 引用"是否已有足够信息，还是需要新增事件（未核实）。
4. 容量上限是否随 GC 上线同时调整。
5. 市场日志压缩的触发方式与是否保留备份。
6. 降级兼容策略（旧版本读快照文件失败时的处理）。

## 9. 实现补充（G1 一键更新与制品回收，R2-11）

本节补充评审结论里"实现前需要补充的设计"，并记录实现与评审结论之间的差异。

### 9.1 与评审结论的差异：权威存储暂未改为当前状态表

评审结论要求把托管安装、选择与信任改为"每个插件一条当前记录"。对照代码后，本 PR 没有改动权威存储的物理格式，原因如下：

- `plugin-authority-log.ts` 的读取路径会从头重放全部操作事件，逐条用同一份策略（`resolveManagedTransition`）校验安装事件、信任事件和操作回执，任何不一致都判为协议错误。`snapshotSync`、`lookupSync`、`commitSync` 的返回值（`heads`、`installEvents`、`operationEvents`、`installations`）被 Server 的组合、安装器、选择管理器、目录投影和 Studio 的修订号检查共同依赖，约 60 个测试文件覆盖它们。
- 信任事件表 `plugin_trust_events` 同时承载手动本地插件的信任，其序号是本地插件来源 `stamp` 和前缀校验的一部分，不能按插件折叠。
- 在同一个 PR 里替换这套协议，并保证"旧数据保留、可重复迁移、失败不丢数据"，风险高于一键更新与回收本身。

因此本 PR 保持现有存储格式不变，不需要迁移；所有已有数据原样保留。已有的 `installSequence`、`trustSequence`、`operationSequence` 继续作为乐观并发的修订号。"当前状态存储与迁移"作为后续独立 PR，建议设计：新增当前状态表和 `migrated_at` 标记，首次启动从现有事件折叠写入，旧表与旧事件保留不删，迁移事务失败时回滚并让 Server 以明确错误拒绝启动。

### 9.2 "旧制品是否仍被引用"的判定

判定分两层，两层都满足才允许删除。

1. **权威是否仍需要（保留集合）**。`managed-artifact-retention.ts` 只重放已记录的操作回执，按顺序维护每个插件的保留摘要集合：
   - 导入操作加入其摘要，包括对已知内容的重复导入（它记录操作但没有安装事件）；
   - 激活操作加入新摘要，并移除被替换的前一个选择；
   - 实际改变状态的卸载操作清空该插件的集合；
   - 最后并入每个插件当前选择的摘要。
   已导入但从未激活的候选继续保留，用户仍可确认激活。判定只依赖历史回执，因此重放旧日志不会改变含义。
2. **运行中是否仍在使用（引用集合）**。`ExtensionCoordinator.retainedGenerations()` 返回当前代与所有尚未释放的旧代及其成员；旧代在其回合结束、`dispose` 完成后才从内部表移除。成员的 `managedIdentity.digest` 就是它加载的制品摘要。无法读取身份的成员按"未知内容"处理，会阻止本轮所有删除。

没有被保留集合引用、也没有被引用集合使用的制品目录（包括从未提交的孤儿）才会删除。被引用集合使用的延后，由定时器（默认 30 秒）和下一次已提交的选择变更重试。无法判定时延后，不删除。

### 9.3 回收的触发与并发

- 回收在 `mutateManaged` 的串行队列内执行，与导入、激活、卸载互斥。导入的"暂存、提交"在同一个队列项内完成，所以回收不会删除一个刚暂存、尚未提交的制品。
- 触发点：任何已提交的选择变更（更新、激活、卸载等）之后；Server 启动并完成首次加载之后（清理旧版本遗留的孤儿和已被替换的制品）；延后的重试。
- 删除先把 `artifacts/<digest>` 重命名到 `staging/<uuid>`，再用现有的受限逐项删除移除。中途崩溃只会留下暂存区的未完成操作，下一次暂存时由 `recoverStaging` 清理。
- `PluginArtifactStore` 新增 `list()` 与 `remove(digest)`；拥有者包装 `OwnedPluginArtifactStore` 对两者同样要求持有租约。64 个制品的上限保留，`assertCapacity` 逻辑不变。

升级后的第一次启动会回收已被替换的旧版本，原有"回退"候选随之消失；这是评审结论第 5 点的结果。

### 9.4 一键更新

- **检测**：`findManagedUpdates` 在已就绪的所有市场来源里查找同 ID 插件，只考虑 `marketplaceCompatibility` 判为兼容的发布，取比当前选择版本新的最大版本。GET `/plugins/managed` 的每个插件可带 `update: { version, source }`，`source` 是该发布的 GitHub 固定提交。
- **预览**：`POST /plugins/managed/:id/update/preview`（空对象）。Server 用发布的来源获取候选，核对获取到的清单与市场登记的清单完全一致，再返回当前与候选的清单、候选摘要、预览编号、`expectedInstallSequence` 与 `expectedTrustSequence`、被替换的当前选择摘要。
- **确认**：`POST /plugins/managed/:id/update`，请求体为 `requestId`、`previewId`、`candidateDigest`、`previousSelection`、`expectedInstallSequence`、`expectedTrustSequence`，全部取自用户看过的预览。Server 先核对它们与预览一致（不一致返回 `plugin-preview-stale`），再导入候选，并核对导入回执里的摘要与 `candidateDigest` 相同、导入前的信任序号等于预览时的值；然后以 `${requestId}` 激活，激活命令的序号取自导入回执的 `decision.after`，所以同一个请求重放时会重建完全相同的命令，走既有的回执重放。信任仍绑定摘要，新摘要在这次确认里被信任并启用。
- **Studio**：已安装行显示"有新版本 vX"和"更新到 vX"；对话框列出新旧清单在能力、各类贡献和权限上的新增与移除（高风险权限沿用现有影响说明）；确认后显示与其他受管操作相同的回执。拒绝时关闭对话框并提示重新审查。"回退"入口已移除，候选区提示旧版本需从来源重新安装。

### 9.5 已知限制

- 已卸载后重新导入同一摘要不会写入新的安装事件，所以目录里该候选的"导入序号"仍是旧值；保留判定使用操作回执，不受影响。
- 更新用 `intent: 'activate'`；`rollback` 意图仍可被服务端接受（历史回执里存在），但 Studio 不再发出。
- 回收失败只记录并重试，不影响用户操作的结果。
